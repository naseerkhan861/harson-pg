## 2. First reproduce and locate the 404

1. In Chrome DevTools select the nested `app-viral-video-replicator` frame, open **Network**, enable **Preserve log**, and click one history item. Filter for `viralVideoTaskDetail`. Record its **method, exact Request URL and path, status, Response body, response headers, and Initiator**. Never share cookies, session tickets, provider tokens, or the full request body in an issue or PR.
2. Repeat for the pricing 404. The Console abbreviates that URL, so copy its **exact path from Network** rather than guessing its spelling.
3. In your server's local, noncommitted `.env`, inspect the current `YIBAI_GATEWAY_EXTRA_PATHS` value. The repository's `.env.example` is a template; it does **not** prove the running gateway's value.
4. Check whether the 404 is **empty and generated by Harson's route gate**, is an **Nginx 404**, or contains an **upstream YiBai error body**. The route gate in `server.js` calls `res.status(404).end()` before its proxy. Gateway logs show method, path, and status without the query string. An upstream 404 needs a different fix.
5. Compare the same history item in the provider's original site under an authorized account. If it also fails there, investigate the task's availability or YiBai's own API. If it works directly and fails only through `ai.harson-base.com`, continue with the gateway checks.

**Do not add a public `/app` or `/app/proxy` catch-all to the allowlist.** This gateway also forwards authenticated requests, so broadening the prefix could unintentionally expose provider operations beyond this workflow.

## 3. Restore the missing detail API narrowly

### Step 3A — short configuration proof

If Network confirms the request is exactly `POST /app/proxy/viralVideoTaskDetail` and the gateway's own allowlist produces the 404, append the **specific path** to the existing comma-separated `YIBAI_GATEWAY_EXTRA_PATHS` in your server's `.env`. Keep all existing entries; for example, if it still has only the sample values:

```dotenv
YIBAI_GATEWAY_EXTRA_PATHS=/assets,/api,/favicon.ico,/version.json,/frame,/app/proxy/viralVideoTaskDetail
```

The current gate accepts `req.path === prefix` (and paths below that prefix). It will then forward the original `POST` and body through `http-proxy-middleware` instead of returning Harson's empty 404. Recreate **the gateway service**, since a running container does not pick up edited environment variables automatically:

```bash
docker compose --profile gateway up -d --no-deps --force-recreate gateway
docker compose logs --tail=100 gateway
```

Retry the history card. A **200 with valid task JSON** and an updated workflow confirms the missing allowlist path was causal. A new upstream **401/403** means investigate provider session/cookies and the expected upstream origin. A remaining **404** means inspect its Response body and compare the direct-provider request before changing more routes.

The pricing endpoint can be tested in the same fashion, but append **its exact verified path** only after copying it from the Network panel. It is secondary to the detail request.

### Step 3B — keep the finished policy precise in the repo

The environment setting is useful for diagnosis, but the generic extra-prefix mechanism is not method- or module-aware. For a reviewed permanent fix, add an explicit exception in the route-policy section of `src/gateway/server.js` (or extract a small pure policy helper) for the observed request:

```js
function isAllowedReplicatorRequest(req) {
  if (req.harsonGatewaySession?.moduleName !== "video-generator") {
    return false;
  }
  return req.method === "POST" &&
    req.path === "/app/proxy/viralVideoTaskDetail";
}

// In the existing route-gate middleware, after getAllowedPrefixes():
const allowedByMenu = prefixes.some(prefix =>
  req.path === prefix || req.path.startsWith(prefix + "/")
);
const allowed = allowedByMenu || isAllowedReplicatorRequest(req);
if (!allowed) return res.status(404).end();
```

Use the **confirmed** upstream path and method if they differ. Add the pricing endpoint with its confirmed method as a separate exact entry if it is needed. Remove the temporary detail path from the generic `YIBAI_GATEWAY_EXTRA_PATHS` after the reviewed policy is deployed, so it does not continue to admit every method at that prefix. Update `.env.example` and the gateway setup documentation to explain the new sub-tool endpoints and keep secrets out of git.

If the gateway lets the request through but YiBai responds 404, compare the nested tool's direct-site request host and path to the gateway's `GATEWAY_UPSTREAM`. The default upstream is `https://cl-base.yibaiaigc.com`; do not assume that its sub-tool API lives on that same host. Add a host-specific proxy route only after a verified, authorized direct-site trace identifies the correct upstream. Preserve the request method/body, session behavior, and path; never redirect API calls to a guessed host.

## 4. Address the separate MP4 failure only after the API responds

When the task-detail call succeeds, repeat the history click with **Disable cache** enabled in DevTools Network. Select the `image.yibaiaigc.com` `.mp4` request and inspect:

- Actual status after redirects, final destination host and IP/address space, `Content-Type`, `Accept-Ranges`, `Content-Range`, and any conditional or `Range` request headers.
- The request's `Origin` and whether the response permits that exact origin. Check `Access-Control-Allow-Origin`, `Vary: Origin`, and credentials settings if applicable.
- Whether the media element uses `crossorigin` or whether the provider extracts video frames to canvas. Cross-origin media used for canvas needs a valid CORS response; simply removing the `crossorigin` attribute can taint the canvas and break frame extraction.
- Whether a clean browser profile, a second network, or the direct YiBai origin loads the same authorized video. The console's “unknown” versus “public” address-space wording calls for checking DNS/redirects as well as CORS; do not treat it as proof that a single response header will solve every case.

Official background: [MDN on video `crossorigin`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video), [MDN on CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS), and [Chrome on Local Network Access](https://developer.chrome.com/blog/local-network-access/).

**Preferred if YiBai controls the CDN:** have YiBai authorize `https://ai.harson-base.com` for the actual CORS-enabled media request, including the response on 200/206 and cache revalidation, if its media service supports that. Verify the result in the nested frame; the top-level `harson-base.com` origin is different.

**If provider-side CORS cannot be changed and the MP4 still fails:** implement a dedicated, **same-origin media relay** under `ai.harson-base.com`, after the existing gateway session check and before the general YiBai route gate. This is a separate, conditional piece of work:

1. Accept only `GET`/`HEAD` for a **fixed** upstream host `image.yibaiaigc.com` and validated, allowlisted media path shapes. Never accept an arbitrary `?url=` or follow redirects to another host. This prevents the relay from becoming an open proxy or SSRF endpoint.
2. Stream bytes; support video `Range` requests and propagate correct 200/206, `Content-Type`, `Content-Length`, `Accept-Ranges`, and `Content-Range`. Do not buffer large MP4 files or share private user media through a public cache.
3. Preserve gateway authentication and do not forward Harson's session cookie or login credentials to the CDN. Verify whether CDN access requires signed URLs before designing their handling.
4. In a **targeted adapter for the nested viral-video-replicator frame**, point the provider's video preview/frame-reading element to the corresponding same-origin relay path. Restrict rewriting to verified `image.yibaiaigc.com` video URLs in this workflow, and test how the provider creates or replaces that element. Do not rewrite every JSON response, every image, or global `fetch`/XHR. If the provider reads the URL through another mechanism, a DOM-only adapter may be insufficient; confirm its actual behavior first.

Deploy the relay only if the detail API is working and the isolated media test proves it is needed. A media relay does not repair a missing task-detail response.

## 5. Confirm what clicking history is supposed to do

The UI has a separate first-step **upload reference video** control and a right-hand **history** list. After both network errors are removed, compare the behavior with YiBai's direct interface:

- If history selection is meant to open a past **result/preview**, accept that result view as success; the first-step upload box may legitimately stay empty.
- If YiBai really supports **reuse this prior video as a new reference**, verify the existing provider control that performs that action. Do not populate an HTML file input or mutate Vue state from Harson without a supported flow; selecting a history result is not necessarily an upload.
- If the direct provider also cannot load this particular record, check a second valid task before concluding the gateway fix is ineffective.

This avoids treating “the upload box remains visible” as the only test of a successfully loaded history record.
